## 0. 先纠正一处事实

Claude 说「你们已有的 UsageStatsPlugin 正好是这个数据源，只差接上」——**不准确，早就接上了**：

| 环节 | 现状 |
|---|---|
| JS → 原生传参 | `LearningSession.tsx:114` 组装 `{enabled, graceMinutes, allowedApps, blockedApps}` → `startStudyTimer()` |
| 原生轮询 | `StudyTimerService.startGuardPolling()`，`GUARD_POLL_MS = 60_000` |
| 前台应用判定 | `getRecentForegroundPackage()`：`queryUsageStats(INTERVAL_BEST, now-10s, now)` 取 `lastTimeUsed` 最新 |
| 三档语义 | `checkForeground()`：允许→不打扰 / 分心→立即提醒 / 未列出→超 grace 提醒 |
| 命中动作 | `warnGuard()` → 只发通知，5 分钟节流。**没有拉回** |

**所以真正的缺口是三个，不在"接线"上：**

1. **粒度**：60 秒轮询 → 做不到"离开 5 秒就算"。而且 `queryUsageStats` 是聚合查询，本身有分钟级延迟，单纯调快间隔既不准又耗电 → 必须换 `queryEvents`。
2. **拉回能力**：现在只会发通知。拉回要靠 `SYSTEM_ALERT_WINDOW`（悬浮窗）才有资格从后台 `startActivity`，Manifest 里**没有**这个权限。
3. **概念重叠**：`blockedApps` 在"默认禁止"下确实零信息量，删得掉。

## 1. 严格模式

### 1.1 数据结构 OLD → NEW

| 位置 | OLD | NEW | 迁移处理 |
|---|---|---|---|
| `ReminderConfig.guardEnabled: boolean` | 开/关两态 | `guardLevel: 'off' \| 'warn' \| 'pull'` | `true → 'warn'`，`false/undefined → 'off'` |
| `ReminderConfig.guardGraceMinutes: number` | 分钟，默认 5 | `guardGraceSeconds: number`，默认 5（秒） | `× 60`；旧值 5 分钟 = 300 秒不变语义 |
| `AppData.globalAllowedApps: string[]` | 无 | **新增**：全局白名单，所有方向共用 | 默认 `[]` |
| `Task.allowedApps: string[]` | 方向白名单（全量） | **语义改为增量**：全局之外的额外放行 | 不动数据，只改语义 |
| `Task.blockedApps: string[]` | 分心名单 | **删除字段** | 迁移时先整体备份到 `learning-manager:data:v1-blocked-backup`，再从数据里删 |
| `Task.sortIndex` / 拖动排序 | 靠 `reorderTask` 数组位移 | 不改结构（数组顺序即权重） | 无 |

> `blockedApps` 直接删的依据：严格模式下"不在白名单"一律同等处理，"更严厉"没有第二档可落。留着只会让用户以为它是第二份名单——这正是当前困惑的根源。
> 但**不能静默丢**：迁移时把旧值 dump 进备份键，写进 `migrate.ts` 注释，必要时可捞回。

`schemaVersion 1 → 2`，迁移函数落在 `migrate.ts`（现有 `migrateAppData` 末尾加一段）。

### 1.2 白名单解析规则（单点收敛）

```
resolveAllowed(task) = 自动放行 ∪ 全局白名单 ∪ task.allowedApps   // 只做加法，不做减法
```

- **不做"方向级排除全局项"**。理由：一旦允许减法，就又出现"全局一份、方向一份"的双份真相，等于把现在的问题换个位置重演。
- UI 上必须分层显示：`继承自全局（N）` / `本方向额外（M）`，两段分开，否则用户还是看不出差别。
- 判定入口统一到 `store.ts` 的 `classifyAppForTask`（现有函数改造），`LearningSession` / `TaskDetail` / `AppListSettings` 全部走它，不再各自读 `task.allowedApps`。

### 1.3 自动放行清单（必须做，否则疯狂误报）

| 类别 | 取法 | 为什么必须 |
|---|---|---|
| 本 App | `getPackageName()`（已有 `selfPackage`） | 否则进自己界面就被判越界 |
| 系统界面 | 硬编码 `com.android.systemui`、`android` | 下拉通知栏、权限弹窗会瞬时占据前台 |
| 输入法 | `InputMethodManager.getEnabledInputMethodList()` 取包名 | 打字时前台是输入法 → 必然误判 |
| 电话 | `TelecomManager.getDefaultDialerPackage()`（API 23+） | 来电界面必须放行 |
| **桌面** | `PackageManager` 解析 `ACTION_MAIN` + `CATEGORY_HOME` | **关键**：按 Home 键后前台是 launcher；不放行则每次回桌面都触发拉回 → 直接死循环 |
| 息屏 / 锁屏 | 监听 `ACTION_SCREEN_OFF` 时暂停判定 | 息屏不该算"离开" |

另外要加**连击确认**：连续 2 次轮询（间隔 3 秒）都命中才动作，过滤来电、验证码弹窗这类瞬时覆盖。

## 4. 一个必须先说的坑：安全区

`targetSdkVersion 36`。Android 15（API 35）起**强制边到边**，Android 16 拿掉了 opt-out。同时 **Android WebView 不实现 `env(safe-area-inset-*)`，恒返回 0** —— 所以 `body{padding: env(...)}` 在真机上等于没写，这就是标签顶进状态栏的真因，改 CSS 改到天亮也没用。

修法（三选一，推荐第 1 个）：

1. **MainActivity 处理 insets**：`ViewCompat.setOnApplyWindowInsetsListener` 给 WebView 或根容器补 `systemBars` 的 top/bottom padding。一处改动，全局生效，Web 层不用动。
2. 引 `@capacitor/status-bar`，用 `setOverlaysWebView(false)` 把 WebView 压到状态栏下方 —— 会丢掉沉浸式效果，且只解决顶部。
3. 原生把 insets 通过 bridge 注入 CSS 变量 —— 最灵活，但要额外维护通道。

## 6. 修订与决定（2026-10-28）

### 6.1 §4「必须手写 WindowInsets」这句是错的 —— 已更正

核对 `@capacitor/android@8.4.2` 源码后确认，**Capacitor 8 已经内建处理，不需要手写**：

| 事实 | 证据 |
|---|---|
| `SystemBars` 由 Bridge 自动注册 | `Bridge.java:658` → `registerPlugin(com.getcapacitor.plugin.SystemBars.class)` |
| 会自动注入 CSS 变量 | `SystemBars.java:265-268` 写入 `--safe-area-inset-top/right/bottom/left`（已换算成 dp） |
| 新版 WebView 下 `env()` 直通 | `SystemBars.java:41` `WEBVIEW_VERSION_WITH_SAFE_AREA_FIX = 140`；WebView 主版本 ≥140 且 `viewport-fit=cover` 时走 passthrough，只给输入法留 padding |
| 旧版 WebView 下原生兜底 | 同文件 199-215 行：给 WebView 父视图 `setPadding(左, 上, 右, 下)` |
| 可用 `insetsHandling` 关掉整套逻辑 | `SystemBars.java:37-38`：`css`（默认）/ `disable` |

**结论：不用改 `MainActivity`，也不用加任何插件依赖。** 本项目 `index.html:7` 已有 `viewport-fit=cover`，
`capacitor.config.ts` 未覆盖 `plugins.SystemBars` → 走默认 `css` 档，上述两条路径都会生效。

那为什么截图里标签还是顶进状态栏？因为问题**不在「安全区没生效」，而在「body 的 padding 挡不住滚动」**：
`body` 确实有 `padding-top: env(...)`，但整页滚动时这段 padding 会跟着内容滚走
（`TaskDetail` 这类页面是整页滚动，不在 `.pool-scroll` 里），内容自然滑到状态栏下面。
padding 只解决「起始位置」，不解决「滚动过程」。

真正的修法（归入 B4）：

1. 把 `env(safe-area-inset-*)` 换成 `var(--safe-area-inset-top, env(safe-area-inset-top))` 降级链，两种 WebView 都吃得住；
2. 让滚动发生在安全区**内部**（`html,body{height:100%;overflow:hidden}` + 内层 `overflow-y:auto`），而不是靠 body padding；
3. 需要滚动时一直可见的标签条（详情页的 内容序列/记录）做成 sticky，并给它自己补上边距。

> 没连真机，上面第 2、3 点是按布局推断的。上机第一件事：量 `--safe-area-inset-top` 的实际值。
> 若为 0，说明这台机器走的是旧 WebView 兜底路径（靠原生 padding），CSS 侧就不用再动。
