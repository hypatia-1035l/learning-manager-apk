# 应用名单功能 · 方案

> 目标：**按学习方向管控应用** —— 每个方向配一份名单（允许 / 分心），只给允许的应用提供入口，且能在计时页直接点击进入。
> 状态：**P1 已实现并出包**（2026-09-14）。P2 / P3 未做。

---

## 0. 结论摘要

| 问题 | 结论 |
|---|---|
| 计时页点击图标进入指定 App | ✅ **可靠**，成本低 |
| 列出已安装应用 | ✅ 可做，需加 `QUERY_ALL_PACKAGES` 权限 |
| 后台自动启动 App | ❌ **做不到**（Android 10+ 后台启动限制，静默丢弃） |
| 物理上"只允许"进白名单 | ⚠️ **做不到**，除非上无障碍服务（不建议） |
| 能落地的最强"只允许" | ✅ **只提供入口 + 越界提醒**（靠 UsageStats 检测） |

**一句话**：入口管制 100% 能做；"打不开别的 App"做不到，只能做到"跑偏了提醒你"。

### 0.1 已定策略（§7 拍板结果）

| 项 | 决定 |
|---|---|
| **默认策略** | **禁止** —— 不在白名单里的应用，一律不给入口 |
| **黑名单语义** | **该方向的分心项**（挂在方向级，不是全局排除层） |
| **白名单粒度** | **方向（Task）级** —— 不下沉到序列级 |
| **P3 越界提醒** | **做，但做成开关**（默认关，见 §6.3） |

> ⚠️ 关于"禁止"的准确含义：在**不上无障碍服务**的前提下，"禁止"只能落成 **不给入口 + 跑偏了提醒**，无法物理阻止你从桌面打开别的 App。这是 Android 的硬边界，不是实现偷懒。

## 1. 已摸清的底

### 1.1 有个半成品死代码（重要）

`android/app/src/main/java/com/learning/manager/UsageStatsPlugin.java` 已实现：

- `hasPermission()` —— 检查「使用情况访问」权限是否已授予
- `requestPermission()` —— 跳系统设置页
- `queryTodayStats()` —— 返回今日各应用前台时长（`packageName` / `appName` / `foregroundMs`）

但：

| 项 | 状态 |
|---|---|
| `PACKAGE_USAGE_STATS` 权限 | ❌ 不在 `AndroidManifest.xml` |
| JS 侧调用 | ❌ `src/` 全树零引用 |

→ **Java 那半边不用重写**，补 Manifest 权限 + 写一个 JS wrapper 即可启用。

### 1.2 依赖现状

- `@capacitor/app-launcher` **未安装**，而且装了也没用 —— 它只能开 `scheme://` / URL，**开不了指定包名的 App**。按包名启动必须自写插件方法。
- 计时基础设施已就位：`StudyTimerService`（前台服务 + 常驻通知）→ 点击进入白名单 App 后，**计时照常跑**，还能从通知一键回计时页。这条链路不用新做。

## 2. 能力矩阵

| 能力 | 实现方式 | 需要什么 | 风险 |
|---|---|---|---|
| 列出已安装应用 | `PackageManager.getInstalledApplications` | `QUERY_ALL_PACKAGES` | 侧载无碍，上架会被拒 |
| 取应用图标 | `getApplicationIcon` → PNG base64 | 同上 | 300+ 图标要懒加载 |
| 按包名启动 | `getLaunchIntentForPackage` + `startActivity` | 无 | 用户点击时 100% 可靠 |
| 读使用时长 | `UsageStatsManager`（已有 Java 实现） | `PACKAGE_USAGE_STATS`（需手动去设置页开） | 权限非运行时弹窗 |
| 检测前台应用（实时） | `UsageStatsManager.queryEvents` 轮询 | 前台服务常驻 | 耗电；聚合查询有分钟级延迟 |
| 后台自动启动 App | ✗ | — | Android 10+ 静默丢弃 |
| 拦截其他 App | ✗ | `AccessibilityService` | 敏感权限、易被杀、不建议 |

### 2.1 关于"后台自动启动"的细节

Android 10（API 29）起引入**后台启动 Activity 限制**。已知豁免途径包括：持有悬浮窗权限（`SYSTEM_ALERT_WINDOW`）、由用户交互触发的 `PendingIntent` 等。**前台服务单独存在并不保证豁免**。

所以按可靠性排序：

1. **用户点击（App 在前台）** —— 最稳，本方案主路径
2. **通知的 PendingIntent** —— 官方豁免口，可做"半自动"（到点发通知，点通知进入）
3. 悬浮窗权限 —— 可尝试，但敏感权限 + 体验差
4. 纯后台自动拉起 —— 放弃

## 3. 数据模型

```ts
// 应用元数据：存包名 + 冗余应用名（卸载后仍可显示）
export interface AppEntry {
  packageName: string   // 唯一键
  appName: string       // 冗余存名
}

// 全局应用池（元数据缓存，非策略载体）
// AppData 增加：
appPool?: AppEntry[]

// 方向名单：挂在 Task 上，两份包名列表
// Task 增加：
allowedApps?: string[]   // 允许：给入口，计时页显示图标
blockedApps?: string[]   // 分心：不给入口，越界时提醒最重
```

**层级选择**：名单挂在 **Task（学习方向）级**（已拍板，不下沉到 Sequence）。理由：一个方向通常就对应一两个 App（阅读→微信读书，绘画→绘图 App），方向级已经够用。若将来发现序列粒度确实需要，再加 `LearningObject.allowedApps` 覆盖，不破坏现结构。

**迁移**：`migrate.ts` 补默认 `[]` / `undefined`，与上次加 `pinnedTasks` 完全同构，零风险。

**`appPool` 的定位**：只做**应用元数据缓存**（包名 → 应用名 / 图标），让跨方向复用时不必反复查询系统。**策略（允许/分心）全部存在 Task 上**，池子本身不带 `list` 字段——避免"池里有立场、方向里也有立场"的双份真相。

### 3.1 三层优先级（核心语义）

同一个包名在某个方向下，只可能是三种身份之一：

| 身份 | 判定 | 计时页入口 | 越界提醒强度（P3） |
|---|---|---|---|
| **允许** | 在 `allowedApps` | ✅ 显示图标，点击直达 | 不提醒 |
| **分心** | 在 `blockedApps` | ❌ 不显示 | **立即提醒**（"这是你定的分心项"）|
| **未列出** | 都不在 | ❌ 不显示 | **超 N 分钟才提醒**（默认宽松）|

规则：
- **允许优先**：若同一包名同时出现在两份名单里（理论上的脏数据），**以 `allowedApps` 为准**，并在设置页给出提示。
- **默认禁止**：未列出 = 不给入口。这是"禁止"策略的落点。
- **分心名单不改入口**：它本来就是不给入口的，加进分心名单的意义在于**提升提醒权重**——你在 P3 里被逮到时，提醒来得更快更硬。

### 3.2 越界提醒的开关与参数（P3）

```ts
// ReminderConfig 增加（或独立 guard 配置）
guardEnabled?: boolean     // 越界提醒总开关，默认 false
guardGraceMinutes?: number // 未列出应用的容忍分钟数，默认 5
```

- `guardEnabled = false` → 整个轮询不启动，零耗电。
- 分心名单命中**不受 `guardGraceMinutes` 保护**，直接提醒。

## 4. 原生插件设计

新建 `AppListPlugin.java`（形态照抄现有 `UsageStatsPlugin`）：

```
@CapacitorPlugin(name = "AppList")

listApps()                    → { apps: [{ packageName, appName, isSystem }] }
getIcon(packageName)          → { ok, dataUrl }   // 懒加载，按需取
launch(packageName)           → { ok, error? }    // getLaunchIntentForPackage + startActivity
```

Manifest 需加：

```xml
<uses-permission android:name="android.permission.QUERY_ALL_PACKAGES" />

<!-- 若同期启用时长统计 -->
<uses-permission android:name="android.permission.PACKAGE_USAGE_STATS"
    tools:ignore="ProtectedPermissions" />
```

> ⚠️ **Manifest 改动需重新签名打包，安装会覆盖并清空现有应用数据** —— 所以 Native 侧一次做齐，别分两次装。

## 6. 分期计划

### P1 · 入口管制 ✅ 已实现（2026-09-14）
1. `AppListPlugin.java`：`listApps` + `getIcon` + `launch` ✅
2. `AndroidManifest.xml`：`QUERY_ALL_PACKAGES` + `PACKAGE_USAGE_STATS` 一次加齐 ✅
3. `src/appList.ts`：Capacitor JS wrapper（含图标缓存）✅
4. `types.ts` / `migrate.ts`：`AppEntry` + `appPool` + `Task.allowedApps` + `Task.blockedApps` ✅
5. 设置页「应用名单」+ TaskEditForm **双名单**多选（选择器复用于同一层 Modal 内）✅
6. 计时页图标行 + 点击启动；方向详情页也加了一行入口 ✅

**产出**：选好方向白名单 → 计时页点图标进入 → 计时继续跑（前台服务）→ 通知栏一键回来。

> 注意：**P1 阶段「分心名单」只存数据、不影响行为** —— 因为默认策略已经是"不给入口"，分心项在 P1 本就进不来。它的价值在 P3 兑现（越界提醒时权重最高）。所以 P1 把 UI 一起做齐，是省一次改动，不是 P1 就有拦截效果。

### P2 · 体验打磨
- `getIcon` 懒加载 + 缓存（避免一次拉 300 个图标卡死）
- 搜索框 + 已安装/已选切换
- 名单里的 App 被卸载 → 灰化 + 提示

### P3 · 管控层（**开关控制，默认关**）
- `usageStats.ts` wrapper 接上现成的 `UsageStatsPlugin`
- 权限引导：检测未授权 → 一键跳「使用情况访问」设置页
- 计时期间轮询前台应用：
  - 命中 **分心名单** → 立即提醒
  - **未列出** 且停留超 `guardGraceMinutes`（默认 5 分钟）→ 提醒
  - 命中 **允许名单** → 不打扰
- **只提醒，不拦截**
- 整个模块由 `guardEnabled` 开关控制，**默认 false** —— 关着时零轮询、零耗电
- 开启后前台服务常驻轮询，间隔放粗（60s）

### P4 · 不建议
- 无障碍服务真拦截（`AccessibilityService`）：敏感权限、易被杀、维护成本高。**除非将来明确要做"锁机"，不碰。**

## 8. 风险与坑

| 坑 | 说明 |
|---|---|
| `QUERY_ALL_PACKAGES` | 自签名侧载无碍；若将来上架应用商店会被审核拒 |
| `getLaunchIntentForPackage` 返回 null | 部分系统应用/无启动入口的 App 会返回 null → 需兜底提示"该应用无法直接启动" |
| 图标体积 | 一次拉 300+ 图标 base64 会卡死 WebView → 必须懒加载 |
| UsageStats 实时性 | `queryAndAggregateUsageStats` 是聚合查询，**有分钟级延迟**，不适合精确实时检测；要实时得走 `queryEvents` 轮询 |
| 重装丢数据 | Manifest 改动 = 重新签名 = 覆盖安装清数据。**P1 就把两个权限加齐** |
| 白名单为空 | 计时页应隐藏图标行，而不是显示空框 |
| "禁止"是软约束 | 默认禁止 = 不给入口，**不是物理拦截**。从桌面仍可打开别的 App，唯一制约是 P3 的提醒。别把它当锁机 |
| 分心名单在 P1 无行为差异 | 默认已禁止入口，分心项 P1 本就进不来；它的效力要到 P3 才兑现。P1 先做 UI 是为了省一次改动 |
| 双名单脏数据 | 同一应用同时进两份名单 → 约定**允许优先**，且 UI 从源头禁用另一侧 |
